# 15_ANTIGRAVITY_GLOBAL_RULES.md

# AntiGravity Global Rules

**Version:** 1.0

**Status:** Mandatory

**Priority:** Highest

---

# 1. Purpose

This document defines the mandatory operating procedures, engineering standards, decision-making process, and quality expectations that AntiGravity must follow throughout the development of the HOPSY PLAZA Electronics E-Commerce Platform.

These rules apply to every task, regardless of size.

No implementation may intentionally violate these standards.

---

# 2. Primary Objective

Your objective is **not** simply to generate code.

Your objective is to function as an experienced multidisciplinary software engineering team responsible for delivering a production-ready enterprise application.

Every decision should prioritize:

* Product quality
* Maintainability
* Scalability
* Performance
* Security
* Accessibility
* User experience
* Long-term consistency

---

# 3. Project Awareness

Before beginning any task:

* Read every project document relevant to the task.
* Understand previous implementation decisions.
* Understand the project architecture.
* Understand the design system.
* Understand existing coding conventions.
* Understand existing component patterns.
* Understand existing APIs.
* Understand existing database models.

Never treat a task as an isolated project.

---

# 4. Skill Discovery & Selection (Mandatory)

Before starting implementation:

## Step 1

Inspect **every available AntiGravity skill**.

Do not assume previously used skills remain the best choice.

---

## Step 2

Understand the responsibility of each available skill.

Evaluate:

* Primary purpose
* Strengths
* Weaknesses
* Specialization
* Compatibility with the current task

---

## Step 3

Select only the skill or combination of skills that best fits the current objective.

Examples include (but are not limited to):

* Architecture
* Backend
* Frontend
* UI Design
* UX Design
* Accessibility
* Performance
* Database
* Security
* Testing
* Documentation

Do not activate unrelated skills.

---

## Step 4

If multiple skills complement one another, combine them intelligently.

Avoid using one skill when multiple specialized skills will produce a better result.

---

## Step 5

Whenever the task changes significantly, repeat the skill selection process.

Never reuse the previous skill selection without re-evaluation.

---

# 5. Planning Before Coding

Never begin implementation immediately.

Always:

* Analyze requirements.
* Identify dependencies.
* Review related modules.
* Review shared components.
* Review reusable utilities.
* Identify possible edge cases.
* Plan the implementation.
* Estimate project impact.

Only then begin development.

---

# 6. Existing Code Comes First

Always inspect the existing project before writing code.

Understand:

* Folder structure
* Existing components
* Existing hooks
* Existing utilities
* Existing APIs
* Existing styling
* Existing patterns

Never duplicate existing functionality.

Always extend existing systems whenever appropriate.

---

# 7. Documentation First

Documentation is the source of truth.

When documentation exists:

Documentation takes precedence over assumptions.

If documentation is unclear:

Analyze the project before making a decision.

Never invent functionality that contradicts documentation.

---

# 8. Design Philosophy

Every interface must feel:

* Premium
* Professional
* Modern
* Purposeful
* Clean
* Trustworthy

Design should never appear AI-generated.

---

# 9. Prohibited UI Patterns

Never generate:

* Generic AI layouts
* Generic SaaS templates
* Generic Tailwind templates
* Huge hero sections
* Floating decorative cards
* Decorative blobs
* Cartoon illustrations
* Emoji-based interfaces
* Glassmorphism
* Neon gradients
* Random glowing borders
* Floating live indicators
* Fake charts
* Fake metrics
* Placeholder dashboards
* Oversized headings
* Empty whitespace without purpose
* Decorative animations without functional value

Every visual element must have a purpose.

---

# 10. Component Standards

Components must:

* Be reusable
* Be composable
* Be responsive
* Be accessible
* Be maintainable
* Be documented
* Be consistent

Avoid one-off components whenever possible.

---

# 11. Responsive Design

Responsiveness is mandatory.

Every page, component, modal, drawer, form, table, navigation element, and interaction must work across:

* Mobile
* Tablet
* Laptop
* Desktop
* Large desktop displays

Responsiveness must be designed from the beginning.

Never treat it as a final polishing step.

---

# 12. Accessibility

Follow accessibility best practices.

Every implementation should consider:

* Keyboard navigation
* Focus management
* Screen readers
* Semantic HTML
* Color contrast
* ARIA attributes where appropriate

Accessibility is a requirement, not an enhancement.

---

# 13. Performance

Performance is a product feature.

Optimize:

* Rendering
* Images
* Network requests
* Bundle size
* Lazy loading
* Code splitting
* Caching
* Database queries

Avoid unnecessary re-renders.

---

# 14. Code Quality

Code must be:

* Clean
* Modular
* Readable
* Typed
* Consistent
* Well organized

Avoid:

* Duplicate logic
* Dead code
* Large components
* Large functions
* Hardcoded business values
* Excessive nesting

---

# 15. TypeScript Standards

Use strict typing.

Avoid:

* any
* unnecessary type assertions
* weak typing

Define reusable interfaces and types whenever appropriate.

---

# 16. Error Handling

Every feature must include:

* Validation
* Error handling
* Loading states
* Empty states
* Success states
* Recovery paths

Never assume requests always succeed.

---

# 17. Security

Always protect:

* Authentication
* Authorization
* Sensitive data
* API endpoints
* Database access

Follow least-privilege principles.

Never expose secrets.

---

# 18. Database Standards

Maintain:

* Proper normalization
* Clear relationships
* Constraints
* Indexes
* Referential integrity

Never compromise data integrity for convenience.

---

# 19. API Standards

APIs must be:

* Predictable
* Consistent
* Version-friendly
* Secure
* Properly validated
* Properly documented

Return meaningful responses.

---

# 20. Design Consistency

Before creating a new component:

Search for an existing one.

Before creating a new pattern:

Search for an existing pattern.

Consistency always outweighs novelty.

---

# 21. Self-Review

Before completing any task:

Review:

* Architecture
* Code quality
* Responsiveness
* Accessibility
* Performance
* Type safety
* Design consistency
* Business logic
* Security

Correct obvious issues before considering the task complete.

---

# 22. Completion Checklist

A task is complete only when:

* Documentation has been followed.
* The correct AntiGravity skills were selected.
* Existing code has been respected.
* No unnecessary duplication exists.
* Design is consistent.
* Responsive behavior has been verified.
* Accessibility has been considered.
* Code quality meets production standards.
* Security has been preserved.
* The implementation is ready for production.

---

# 23. Definition of Excellence

Success is not measured by the amount of code written.

Success is measured by delivering software that:

* Solves the intended business problem.
* Integrates cleanly with the existing system.
* Feels cohesive and intentional.
* Demonstrates professional engineering discipline.
* Meets production-quality standards.
* Reflects thoughtful design rather than automated generation.
